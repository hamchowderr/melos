### 1.2.1 Origin research used by this contract

Supplied by the coordinator on 2026-09-12 from GIZMO creator material (YouTube video `O4byGh9mOc4`) and archived GIZMO+ pages. Recorded as [SRC-002].

- "One Stop Ready" means the owner can say "do I own everything … can you just deal with me": one party clears both the master side and the publishing/sync side, so a licensee deals with a single contact. §6.5 derives readiness from this.
- The legacy report is plain text first. It is pasted into emails and into Disco track info/comments for licensing agents. Sections toggle on and off, and lyrics come last. §7.7 keeps text primary and PDF secondary.
- The legacy pitch model is a song × client matrix. Licensing agents are the main client type; music supervisors, music libraries, ad briefs, labels, bloggers and radio are also targets. GIZMO+ sales copy tracks "who passed or would like more info". §6.4 keeps `requested_more`.

### 1.4 Conventions

- IDs are TEXT ULIDs generated by the application (supervisor decision 2026-09-12). Entity and aggregate tables carry a type prefix: `ws_` workspace, `mig_` migration run, `cad_` control audit row, `pty_` party, `cmp_` composition, `ctr_` composition contributor, `rec_` recording, `lnk_` recording link, `rel_` release, `trm_` metadata term, `agr_` agreement, `lic_` licensing contact, `con_` contact, `pit_` pitch, `pti_` pitch item, `pev_` pitch event, `msg_` message, `ast_` asset, `tpl_` report template, `rpt_` generated report, `aud_` audit row, `imp_` import run, `iss_` import issue, `xref_` external reference. Child relationship rows use bare ULIDs: `contact_methods`, `artist_aliases`, `party_identifiers`, `party_society_affiliations`, `composition_alt_titles`, `recording_artists`, `recording_contributors`, `publishing_interests`, `master_interests`. Better Auth tables keep the ids Better Auth generates at runtime; a seed may supply its own (the demo fixture uses `usr_<ulid>` for users). Agent thread ids are generated by the CopilotKit client and stored as given.
- Timestamps are ISO-8601 UTC TEXT in Melos tables. Better Auth tables use the integer epoch-millisecond columns its Drizzle schema generates (§11). Calendar dates are `YYYY-MM-DD` TEXT.
- Ownership shares are INTEGER basis points, 0–10000. 100% = 10000.
- Identifiers are stored normalized: uppercase, no separators, no display prefix. ISRC is stored as 12 characters (`USDMO2600001`), ISWC as 11 (`T9000000010`). The UI formats them for display.
- Booleans are INTEGER 0/1 with a CHECK.
- Referential integrity: the DDL declares foreign keys, but Melos does not rely on SQLite enforcing them on remote Turso connections. `@libsql/client` over HTTP opens a new Hrana stream for each `execute`, `batch` and `transaction` call, and each stream is its own SQLite connection ([SRC-095], [SRC-094]). The parameterized `batch` and `transaction` calls that services use send `BEGIN` before the first statement the caller supplies, so a caller cannot place a pragma ahead of it; only `client.migrate()` sends `PRAGMA foreign_keys=off` before `BEGIN` in the same Hrana batch, to turn enforcement off for schema changes ([SRC-095], `lib-esm/http.js`, `lib-esm/hrana.js`). SQLite ignores `PRAGMA foreign_keys` inside a transaction ([SRC-093](https://sqlite.org/foreignkeys.html)). `IntegrityGuard` therefore applies every declared foreign-key rule, including CASCADE and SET NULL, inside each service transaction (§4.4, DAT-001, ADR-025). U-07 is closed: on 2026-09-13 a remote `@libsql/client` 0.18.0 connection that sent no pragma to a Turso Cloud workspace database created by the preview returned 1 for `PRAGMA foreign_keys` and refused an `artist_aliases` row whose `party_id` did not exist with `SQLITE_CONSTRAINT`. This is behavior observed on that connection, not a guarantee, and Melos does not rely on it: `IntegrityGuard` applies every rule, and declared foreign keys stay defense in depth (ADR-025).
- Totals, readiness and follow-up-due are derived and never stored (ADR-017). The only stored projections are `pitch_items.current_status` and `pitches.last_contacted_at` (the latest `message_sent`, `call` or `meeting` event on the pitch), written in the same transaction as the `pitch_events` row that changes them.

### 1.5 Repository layout

Supervisor decision 2026-09-12: one Next.js app at the repository root, not a monorepo. One Vercel deployable fits the embedded-Mastra decision (ADR-016), and the `src/mastra` module boundary keeps the agent splittable into its own service later.

| Path | Holds |
|---|---|
| `src/app` | Routes and pages, including `src/app/api/auth` (Better Auth handler) and `src/app/api/copilotkit/[[...slug]]/route.ts` (§7.1) |
| `src/mastra` | The Mastra agent and tools (§3), including `readTenantContext`. Must not import from `src/app`. |
| `src/server/services` | Authorization, validation, transactions and audit: `CatalogService`, `RightsService`, `ContactService`, `PitchService`, `OutreachService`, `ReportService`, `ImportService`, `AssetService`, `AuditWriter`, `IntegrityGuard`, `TenantContextResolver`, `WorkspaceProvisioner`, `MelosAgentRunner`, and the `EmailTransport` and `AssetStorage` adapters |
| `src/server/auth` | The Better Auth instance and configuration (organization plugin, access control in §6.2, `organizationHooks`), used by `src/app/api/auth`, `TenantContextResolver` and `WorkspaceProvisioner` |
| `src/server/db` | Control-plane, workspace and agent-runtime clients; migrations (`src/server/db/migrations/control` for drizzle-kit, `src/server/db/migrations/workspace` for numbered workspace SQL, which runtime code applies from the generated `src/server/db/workspace-migrations.generated.ts` (§7.2), `src/server/db/migrations/runtime` for `agent_threads` and `agent_thread_runs`; Mastra creates its own storage tables); the generated foreign-key rules `src/server/db/fk-rules.generated.ts` (§4.4); `MigrationRunner` |
| `src/components` | UI shared by chat rendering and full-page views (§2.3) |
| `tests/unit`, `tests/integration`, `tests/e2e` | Test IDs ending in `-UNIT-`, `-INT-` and `-E2E-` respectively |
| `fixtures/aimock` | Versioned AIMock fixtures (TST-AI-004, §5.8) |

Dependency direction: `src/app` may import `src/mastra`, `src/server` and `src/components`; `src/mastra` may import `src/server`. `src/server`, including `src/server/auth`, imports neither `src/app` nor `src/mastra` (P-38), so services stay callable from the traditional UI, the agent and the importer alike.

## 3. Canonical tool contracts

### 3.1 Rules for every tool

- Each tool is a Mastra `createTool` with `inputSchema` and `outputSchema` ([SRC-038](https://mastra.ai/reference/tools/create-tool)). Tools read tenant values only through the typed `readTenantContext` helper, which returns an error result before any service call when a key is missing (§7.1).
- Required request context keys, set only by `TenantContextResolver` (§7.1): `userId`, `organizationId`, `workspaceId`, `workspaceRole`, `requestId`.
- Tools call services. Services own authorization, transactions, validation, integrity checks (§4.4), database access and audit. Tools hold no SQL and no authorization logic (ADR-010, BP §18).
- Inputs take stable IDs. Name resolution is a separate read (`searchMusic`, `searchContacts`) that follows §3.5. Only genuinely distinct matches render `ConflictResolver` (BP §15.2, §17.2).
- An entity ID that does not exist in the active workspace database returns `NOT_FOUND`. Because each workspace has its own database, an ID from another workspace can never resolve (TEN-001).
- Tools return full DTOs to the UI and the compact, ID-bearing summary in §3.6 to the model through `toModelOutput` ([SRC-038](https://mastra.ai/reference/tools/create-tool)). Tool results never carry database credentials, provider keys or storage secrets (TEN-008). Contact email addresses, phone numbers, lyrics and report text are not sent to the model (BP §15.2).
- A structured result renders its component. Text-only answers are allowed only for zero results and plain explanations (TS §12).

### 3.2 Risk classes and approval

| Risk class | Meaning | Approval |
|---|---|---|
| `read` | No writes. | Never. |
| `draft` | Writes a draft or note with no external effect. | Never. The result renders visibly. |
| `write` | Canonical write that is easy to review and reverse. | Only on the triggers listed per tool. |
| `write-sensitive` | Ownership, representation or licensing facts. | Always, when the agent calls it (§6.3). |
| `external` | Leaves the system: sending a message. | Always. |

Triggers that force approval on any write tool: more than one entity changed in one call (bulk), any delete, a change or clearing of an identifier (ISRC, ISWC, UPC/EAN, copyright registration number), and create calls where a possible duplicate exists. Approval uses tool suspension with state re-validation on resume (§7.4). Requests, grants, declines and stale approvals are audited (AUD-002, AUD-003).

### 3.5 Name resolution and song grouping (CAT-009)

A seeded or imported song is a composition plus one recording with the same title. Search must treat that pair as one song.

- **Grouping.** `searchMusic` returns one `MusicSearchResult` per composition, carrying all of its live recordings. A recording without a composition is its own result. Releases never form separate results in chat; `/catalog` search lists them (`SearchResults`).
- **Primary recording.** `primaryRecordingId` is the only live recording whose normalized title equals the composition title and whose `version_title` is NULL. It is NULL when there is no such recording or more than one. A composition with exactly one live recording uses that recording.
- **Normalization.** Lowercase, trimmed, internal whitespace collapsed to one space. Alternate titles participate.
- **Resolution rule for the agent.**
  1. Exactly one result has `matchType` exact_title or exact_alt_title: use it.
  2. No exact match and exactly one result: use it.
  3. Otherwise (two or more exact matches, or no exact match and two or more results): render `ConflictResolver` with the candidates.
  4. When a tool needs a recording and the chosen song has several recordings: use `primaryRecordingId`; if it is NULL, render `ConflictResolver` with that song's recordings.
- **FTS query building.** The service trims the user text first; text with no tokens after trimming returns an empty result without running a query, because an empty `MATCH` expression is an FTS5 syntax error (checked with SQLite 3.50.4). Otherwise it builds the FTS5 `MATCH` expression: split on whitespace, keep at most 12 tokens, wrap each token in double quotes after doubling every embedded double quote, append `*` after the closing quote of the last token, and join with spaces ([SRC-100](https://sqlite.org/fts5.html): quoted strings, doubled quotes, prefix `*` outside the quotes). The expression is passed as a bound parameter; user text is never concatenated into SQL. Exact title matches are found with an indexed equality query before FTS runs.

### 3.7 Rollup, reference, priority and rebalancing rules

- **References to earlier turns.** "This", "that song" and similar resolve in order: (1) AG-UI context `focusedEntity`; (2) the most recent tool result in the thread whose entity type fits the tool; (3) ask. "Send it" resolves to the most recent `MessageDraftDTO.messageId` in the thread. Renderers of `MusicWorkspaceCard`, `RightsPanel`, `PitchCard` and `MessageDraftCard` set `focusedEntity` to the entity they show (U-04).
- **Has-heard rollup (P-36).** A contact has heard composition C when any of that contact's pitch items targets C or one of C's recordings and either `current_status` is not in (`draft`, `not_contacted`, `archived`), or `current_status` is `archived` and the status before archiving (the `from_status` of the cell's latest `status_changed` event to `archived`, §6.4) is not `draft` or `not_contacted`. For recording R, items on R or on R's composition count. `plannedNotContacted` lists contacts that have not heard the song and have a non-archived `draft` or `not_contacted` cell on it. `neverPitched` lists every other active contact: no cell on the song, or only cells archived from `draft` or `not_contacted`. Such an archived cell is neither heard nor planned.
- **Role rank.** `licensing_agent`, `music_supervisor`, `music_library`, `ad_agency`, `record_label`, then all other roles; ties by display name.
- **Follow-up priority (P-31).** `followUpsDue` holds cells whose `followUpDue(D)` is true for the requested date D (§6.4), ordered by: (1) whole days between `nextFollowUpAt` and D in the member's timezone, most first; (2) status rank `requested_more`, `interested`, `responded`, `awaiting_reply`, `sent`; (3) contact role rank; (4) `nextFollowUpAt` ascending; (5) `pitchItemId`. `priorityRank` numbers the result from 1.
- **Share rebalancing (P-29).** When the user sets one holder's share without saying how to rebalance: with exactly one other holder in the set, that holder receives `10000 − new share`; with two or more other holders, the agent asks and never distributes on its own. The same rule applies to writers, to one publishing territory, and to masters. The full proposed set appears in `ConfirmationCard` before and after.
- **Report items (P-37).** `previewReport` and `generateReport` require `items`. When the user names no song, the agent uses `focusedEntity`, then `selectedEntities` in order; when neither is set, it asks. It never defaults to the whole catalog. A `compositionId` item expands to its primary recording when there is one; otherwise the report shows composition sections only for that song.

## 4. Canonical DDL

SQLite/libSQL dialect. Control-plane migrations live in `src/server/db/migrations/control` (drizzle-kit); workspace migrations are numbered SQL files in `src/server/db/migrations/workspace` (§1.5), embedded in a generated module for runtime code (§7.2). Each file is `NNNN_<name>.sql`, numbered from `0001` without gaps or duplicates, its statements separated by `--> statement-breakpoint`. Each version runs in one `client.migrate()` call together with its `schema_migrations` row, whose `name` is the part after the number: one transaction per version (§7.2). That transaction also creates `schema_migrations` when it is missing, so no migration file declares it and version 0 is an empty database. Turso Multi-DB Schemas is not used: it is deprecated for new users ([SRC-013](https://docs.turso.tech/features/multi-db-schemas), fetched 2026-09-12).

### 4.1 Control plane (`melos-control`) and agent runtime (`melos-agent-runtime`)

### 4.4 Design notes

- **Party supertype (ADR-013).** BP §5 attaches identifiers, society affiliations and contact methods through `party_kind` + `party_id` with no foreign key, and uses paired nullable columns (`publisher_organization_id` / `publisher_person_id`) with XOR checks elsewhere. Neither can be enforced by a foreign key. One `parties` table gives every relationship a single foreign key column. BP App A already targets `publisher_party_id` and `owner_party_id`, so the supertype matches the legacy field map.
- **Kind checks.** Where a relationship needs a specific kind (writers and the writer self party are people; a contact's company is an organization), the child carries a kind column and a composite foreign key to `parties(id, party_kind)`. SQLite does not require a parent row when any child key column is NULL ([SRC-093](https://sqlite.org/foreignkeys.html)), so optional links still work.
- **Referential integrity (DAT-001, ADR-025).** Declared foreign keys are the source of the rules, not the enforcement (§1.4). The rules are generated: a build step migrates an empty copy of `melos-control`, of the workspace schema and of `melos-agent-runtime`, reads `PRAGMA foreign_key_list(<table>)` for every table (columns `id`, `seq`, `table`, `from`, `to`, `on_update`, `on_delete`, `match`; [SRC-104](https://sqlite.org/pragma.html), column names checked with SQLite 3.50.4), and writes `src/server/db/fk-rules.generated.ts`. CI fails when the committed file differs from a fresh generation. Inside each service transaction `IntegrityGuard` applies, for all three databases:
  1. **Insert and update.** Every non-NULL child key has a parent row; a composite key is checked only when all its columns are non-NULL, as SQLite does ([SRC-093]). A column the write omits is checked with the value the write stores, such as its default. A new reference to a soft-deleted parent is refused. Party kind follows from this rule, because kind-checked relationships are composite keys to `parties(id, party_kind)`. An update that changes a referenced parent column (a `to` column in the generated rules, which includes `parties.party_kind`) is refused with `REFERENCED` while any child row references the old value through a key that includes that column. All declared `ON UPDATE` actions are `NO ACTION`, so the guard never rewrites children; reclassifying a party's kind (P-22 review) first moves or removes its kind-checked references.
  2. **Delete, per the child's `on_delete` action.** `RESTRICT` and `NO ACTION` refuse with `REFERENCED` and the counts; `CASCADE` deletes the child rows first and applies these rules to them recursively; `SET NULL` sets the child columns to NULL. A soft delete sets `deleted_at`, `updated_at` and `updated_by` on live rows and applies only the `RESTRICT` and `NO ACTION` check, counting only live child rows (`deleted_at IS NULL`) when the child table has `deleted_at`; a hard delete counts every child row, because a soft-deleted row still references its parent. Every row deletion goes through the guard, including deletions a service makes implicitly: removing a writer in a share-set replace cascades to `composition_contributor_roles`, and deleting an artist alias sets `recording_artists.artist_alias_id` and `party_identifiers.artist_alias_id` to NULL.
  3. **Song level in pitches.** A pitch never holds a composition cell together with a cell for one of its recordings. Triggers in §4.3 enforce this on insert and when a recording moves to another composition (`recordings_composition_change_pitch_level`); the guard runs the same checks first so the service can return a readable error: it refuses with `SONG_LEVEL_CONFLICT`, and `counts` holds the number of written `pitch_items` or `recordings` rows that would hold a song at both levels.
  Better Auth writes its own tables through its adapter, not through services. Before the adapter deletes an organization or a user, a Better Auth hook deletes it through the guard in one transaction, the organization's `workspace_registry` row first, so every row the rules reach goes with it and the adapter's own deletes match nothing (ADR-030). DAT-INT-001 runs every service operation's integration tests, plus Better Auth organization and user deletes, on connections with `PRAGMA foreign_keys = OFF`, and asserts that `PRAGMA foreign_key_check` returns no rows for the affected database after each operation. SQLite reports violations through that pragma while enforcement is off (checked with SQLite 3.50.4).
- **Deletes.** Parties and music use soft delete. Rights (`composition_contributors`, `publishing_interests`, `master_interests`, `licensing_contacts`), pitch and report tables reference them with `ON DELETE RESTRICT`, so hard-deleting a song or party cannot silently drop shares. Only an explicit admin reassignment workflow hard-deletes (BP §6 Deletion). Credits, links, terms and alternate titles cascade with that hard delete. Pitches are archived, never deleted.
- **Share replacement.** The share tools replace a full set by upserting on the natural key: (`composition_id`, `party_id`) for writers, (`composition_id`, `publisher_party_id`, `territory`) for publishing, (`recording_id`, `owner_party_id`) for masters. Rows in both sets keep their id; rows missing from the new set are deleted. `external_references` points at share rows by natural key (`<compositionId>|<partyId>`, `<compositionId>|<partyId>|<territory>`, `<recordingId>|<partyId>`).
- **Writer shares count once.** `composition_contributors` has one row per writer party per composition; the roles a writer holds live in `composition_contributor_roles`. A composer who is also the lyricist contributes one share.
- **Identifier uniqueness.** ISRC, ISWC and UPC/EAN are unique among live rows through partial unique indexes with `deleted_at IS NULL`, so a soft-deleted song does not block re-entering its identifier.
- **Deliberate polymorphic tables.** `audit_log`, `control_audit_log` and `external_references` keep `entity_type` + `entity_id` without foreign keys. Audit rows must survive the deletion of what they describe. Services remove `external_references` rows in the same transaction as a hard delete.
- **Publishing territory (RGT-007, P-05).** A composition has either one `WORLD` share set or one share set per country, not both. Each set totals 10000.
- **Pitch cells (§6.10).** `pitch_items` holds exactly one of composition or recording. Within one pitch a song appears once: triggers reject a composition cell next to a cell for one of its recordings, and the partial unique indexes reject duplicates at the same level. Cell targets are immutable. `PitchService` also refuses a second open cell (status not in closed_won, closed_lost, archived) for the same contact and song across different pitches.
- **Messages.** `sent` requires `sent_at`; inbound messages are exactly the `received` ones and require `received_at`.
- **UPC/EAN** is non-empty TEXT of digits so leading zeros survive (BP §2.2).
- **Runner tables.** `agent_threads.thread_id` is the primary key, so a thread id has exactly one owning resource. Every runner read and write filters on both `thread_id` and `resource_id` (§7.9).

## 6. Conflict resolutions

### 6.1 Authentication baseline

**Conflict.** BP §14.3 and App C.2 say "existing auth remains authoritative", and BP §5 defines its own membership table in the control plane. TS §5 (ADR-003, ADR-004) freezes Better Auth with Organizations.

**Decision.** Better Auth with the organization plugin is the only authentication and membership system. A Better Auth organization is a Melos workspace, linked 1:1 through `workspace_registry`. Membership and roles live in the Better Auth `member` table, and the control plane has no second membership table. Better Auth tables live in `melos-control`. `npx auth generate` emits their Drizzle schema, and drizzle-kit applies every control-plane migration, separately from workspace migrations (AUTH-006, §4.1).

**Reason.** The ADRs record Better Auth as a user decision. BP's wording assumes a repository with working auth; the Melos repository was created empty on 2026-09-12, so no existing auth exists to preserve. SA §7 ranks BP below TS where TS supersedes it. The organization plugin provides the organization, member and invitation tables, `session.activeOrganizationId`, and `organizationHooks.afterCreateOrganization` for provisioning ([SRC-021](https://better-auth.com/docs/plugins/organization)). Gate A selected the Drizzle adapter with `provider: "sqlite"` ([SRC-024](https://better-auth.com/docs/adapters/drizzle), [SRC-091]); drizzle-kit owns control-plane migrations.

### 6.2 Viewer role and permission matrix

**Conflict.** TS §13 has a Viewer column. Better Auth's organization plugin ships only `owner`, `admin` and `member` ([SRC-021](https://better-auth.com/docs/plugins/organization)).

**Decision.** `viewer` is a custom role built with Better Auth access control (`createAccessControl`, `ac.newRole`, passed through the plugin's `roles` option). Defining custom roles overrides the predefined permissions of those roles, so the statement merges `defaultStatements` and each default role merges its default permissions ([SRC-021](https://better-auth.com/docs/plugins/organization)). The exports `defaultStatements`, `ownerAc`, `adminAc` and `memberAc` from `better-auth/plugins/organization/access`, and the `statements` property of a role, are confirmed in the installed `better-auth` 1.7.4 ([SRC-102]).

```ts
import { createAccessControl } from "better-auth/plugins/access";
import { adminAc, defaultStatements, memberAc, ownerAc } from "better-auth/plugins/organization/access";

const statement = {
  ...defaultStatements,
  catalog:  ["read", "create", "update", "delete"],
  rights:   ["read", "update"],
  contact:  ["read", "create", "update", "delete"],

  outreach: ["draft", "send"],
  report:   ["read", "generate"],
  import:   ["run"],

  ...ownerAc.statements,
  catalog: ["read", "create", "update", "delete"], rights: ["read", "update"],
  contact: ["read", "create", "update", "delete"], pitch: ["read", "create", "update"],
  outreach: ["draft", "send"], report: ["read", "generate"], import: ["run"],
});
export const admin = ac.newRole({
  ...adminAc.statements,
  catalog: ["read", "create", "update", "delete"], rights: ["read", "update"],
  contact: ["read", "create", "update", "delete"], pitch: ["read", "create", "update"],
  outreach: ["draft", "send"], report: ["read", "generate"], import: ["run"],
});
export const member = ac.newRole({
  ...memberAc.statements,
  catalog: ["read", "create", "update"], rights: ["read", "update"],
  contact: ["read", "create", "update"], pitch: ["read", "create", "update"],
```

### 6.3 Approval for rights edits

**Conflict.** BP App B marks share updates "Write/approval for bulk". TS §11 marks them `write-sensitive` with HITL "Yes", and BP §7.4 lists "overwrite ownership" among actions requiring explicit confirmation.

**Decision.** Every agent call to `updateWriterShares`, `updatePublishingShares`, `updateMasterShares`, `attestRepresentation` or `updateLicensingContacts` suspends for approval, whether it touches one row or many (ADR-014). In the traditional UI, the explicit Save in `RightsSplitEditor` is the confirmation; no extra approval step is added there. Both paths write `audit_log`.

**Reason.** Two of three statements in the sources require confirmation. Ownership, representation and licensing contacts decide who gets paid and who can clear a license, so a single wrong row is as costly as a bulk change.

**Decision.** `previewReport` never persists. `generateReport` persists an immutable snapshot (`generated_reports`, `generated_report_items`) and an optional PDF. Attaching a report to a pitch or message always uses a generated snapshot (BP §13.2).

### 6.10 Pitch granularity

**Conflict.** BP models a pitch as one contact plus many items with one status on the pitch; the legacy Pitching Status table is one song + one client + one status; SA §5 lists single versus multiple recordings per pitch as unresolved.

**Decision (P-11, ADR-021).** A pitch is outreach to one contact and holds one or more items. **Decision.** Party supertype (ADR-013, §4.4).

### 6.17 Database engine and client

**Conflict.** SA §4 says to name the data layer "Turso / SQLite-compatible" and to choose the concrete engine or client after a spike, because current Turso docs distinguish the newer Turso Database engine from libSQL. BP §4 says Turso/libSQL.

**Decision.** `@libsql/client` 0.18.0 (Gate A pin, [SRC-090]) against Turso Cloud databases in deployed environments and local libSQL files in development (ADR-024). `@tursodatabase/database` and Turso Sync are not used at MVP. U-26 is closed: `@libsql/client` 0.18.0 connects from Vercel Functions to Turso Cloud with per-database tokens, proven on the preview deploy `melos-bk0lx3k52-otaku-solutions.vercel.app` on 2026-09-13 (§10.2).

**Reason.** Gate A proved the stack with `@libsql/client`, and local-first sync is outside the MVP (BP §4.2).

### 6.18 Referential integrity on remote connections

**Conflict.** BP §4.4 requires foreign-key enforcement on every connection. Review M4 asks for `PRAGMA foreign_keys = ON` at the start of every batch and transaction.

**Decision.** `IntegrityGuard` enforces the rules in service code (§4.4, DAT-001, ADR-025). Declared foreign keys stay as defense in depth.

**Reason.** The parameterized `batch` and `transaction` calls that services need send `BEGIN` before any statement the caller supplies, so a caller cannot put the pragma first. `client.migrate()` does send `PRAGMA foreign_keys=off` before `BEGIN` in the same Hrana batch, but only to turn enforcement off for schema changes, and it sends `PRAGMA foreign_keys=on` at the end ([SRC-095]: `lib-esm/http.js`, `lib-esm/hrana.js`). SQLite ignores `PRAGMA foreign_keys` inside a transaction ([SRC-093](https://sqlite.org/foreignkeys.html)). Each `execute` runs on its own stream, which is its own SQLite connection ([SRC-094], [SRC-095]), so a pragma sent in a separate call does not carry over.

### 7.2 Workspace provisioning and database resolution

- `organizationHooks.afterCreateOrganization` ([SRC-021](https://better-auth.com/docs/plugins/organization)) calls `WorkspaceProvisioner`:
  1. Insert `workspace_registry` with `status = 'provisioning'` and write `control_audit_log`.
  2. Deployed environments (Turso Cloud, ADR-026): create the database with `POST /v1/organizations/{organizationSlug}/databases` and body fields `name` and `group` ([SRC-017](https://docs.turso.tech/api-reference/databases/create)); `organizationSlug` is the Turso organization, not the Better Auth organization. Mint a token with `POST /v1/organizations/{organizationSlug}/databases/{databaseName}/auth/tokens` and the query parameter `authorization=full-access`; the response field is `jwt` ([SRC-018](https://docs.turso.tech/api-reference/databases/create-token)). Store it encrypted in `db_token_ciphertext` with a key held only in the server environment (P-08). Group tokens are not used (ADR-031). Development: a libSQL file `.data/melos-ws-<ulid>.db`.
  3. Apply all workspace migrations, seed system report templates and the `workspace_settings` row, set `schema_version` and `status = 'active'`. Provisioning and `MigrationRunner` apply the workspace migrations embedded as `EMBEDDED_WORKSPACE_MIGRATIONS` in `src/server/db/workspace-migrations.generated.ts`, never the SQL folder, which a Vercel function bundle does not include. `npm run db:workspace-migrations` generates the module from `src/server/db/migrations/workspace`, with each file's `version`, `name`, `file` and `statements`, and `tests/integration/workspace-migrations.test.ts` keeps the two in parity: it fails, naming that script, when a migration is added, removed or edited in the folder without regenerating the module.
  4. On failure set `status = 'failed'` with `status_detail`; the organization stays and provisioning can be retried (P-23): `npm run workspace:provision -- <organizationId>` retries one workspace and `npm run workspace:provision -- --all-failed` every `failed` one, printing only organization ids and statuses (ADR-032).
- Every provisioning attempt, from `afterCreateOrganization` or the retry command, claims the registry row before step 2, and only the claim's owner writes the row afterwards. An attempt that finds a live claim returns the row unchanged, and an attempt that lost its claim writes nothing more. When that attempt then finds the row gone or `deleting`, a delete went past its stale claim, possibly before the host's create finished, so it deletes that database through the same host, logging only the organization id, the step and the error name and code if that delete fails; a row another attempt holds keeps its database, which that attempt uses (ADR-032).
- `organizationHooks.beforeDeleteOrganization` deletes the workspace database before its registry row, so no database outlives the row that names it (TEN-001). A failure, crash or IntegrityGuard refusal after step 1 leaves the organization with a `deleting` row, and deleting the organization again resumes at step 2:
  1. Set `status = 'deleting'` with one committed conditional `UPDATE` that matches only the `status`, `updated_at` and `attempt_id` the delete read. A `deleting` row is not served (§7.1 step 2.3) and not provisioned. While the row is `provisioning` and its claim is live (`updated_at` within `STALE_CLAIM_MS`), or when that `UPDATE` matches nothing because a retry claimed the row after the delete read it, the delete is refused with 503 `WORKSPACE_DELETE_FAILED` at step `provisioning_in_progress` (code `WorkspaceClaimHeld`) and the row keeps its status (ADR-032).
  2. Delete the database through the workspace host, which treats a missing database as deleted (ADR-031). On failure keep `deleting`, set `status_detail` to the step with the error name and code, never the message, and refuse the organization delete with 503 `WORKSPACE_DELETE_FAILED`, logging only the organization id, the step and the error name and code, never a message, token or `status_detail`. An `unconfigured` host skips the delete only when `database_url` is empty and `status_detail` is `create_database failed: WorkspaceHostConfigError`, as on production rows today: that create never reached a host, so no database exists. A Turso create can create the database and then fail while minting its token or reading its hostname, which leaves `database_url` empty with another `status_detail`, so an `unconfigured` host refuses every other row with 503 before step 1: the row keeps its status, and an `active` workspace is never left `deleting`. A retried provisioning overwrites `status_detail`, so a database that a configured host created without storing its URL, followed by a retry while the host was unconfigured, is not deleted; `workspace.deleted` keeps its `database_name`.
  3. In the transaction that deletes the organization (ADR-030), append `workspace.deleted` with the row, without `db_token_ciphertext`, in `before_json`, then delete the registry row through IntegrityGuard, cascading `migration_runs`. Mastra threads and `agent_threads` rows (§7.3) are deleted from phase 5, when `agent_threads` exists.
- `TenantContextResolver` keeps one `@libsql/client` client per workspace id, created with the decrypted token: services call `getWorkspaceDatabase(workspaceId)` in `src/server/services/workspace-connections.ts` with the `workspaceId` of the context resolved for the request, and get a drizzle database over the generated workspace tables. The first call reads the `active` registry row, opens the client with `openWorkspaceDatabase` and keeps it in a module-level map; a failed open is not kept. The resolver checks the registry status on every request before any service asks for the database, and that check is the gate: a request that already passed it may finish on the cached client, for example while a migration batch sets the row `migrating` a moment later. No connection-level state is assumed: over HTTP every call runs on its own stream (§1.4). The URL and token exist only inside that cache, in the client's private fields, never in `TenantContext`, request context values, tool inputs or outputs, or logs; a failed registry lookup, open or read throws `WorkspaceConnectionError` with the workspace id and the error name and code, never a message (TEN-008). Services never let a raw error from a workspace database or the registry escape, because its message may hold a URL or token; they report it through `errorCode`, as `checkWorkspaceDatabase` does. U-26 is closed: on the preview deploy `melos-bk0lx3k52-otaku-solutions.vercel.app` on 2026-09-13, the `ping` tool, which reads the workspace database through `checkWorkspaceDatabase`, ran in Vercel Functions for two users and returned each user's own `workspaceId` and `organizationId` (§10.2).
  - Deleting a workspace closes and forgets its client once the row is `deleting` (step 1) and before its database is deleted (step 2), which drops the token; a `deleting` row opens no new client. Other server instances keep their entry until they recycle: the resolver refuses the workspace, and workspace ids are ULIDs that are never reused, so the entry serves nothing. On Windows, a closed `@libsql/client` 0.18.0 file client keeps its file open until garbage collection finalizes its statements, so the local host's delete can fail with `EPERM` right after the workspace was used; the organization delete answers 503 and deleting it again completes once the file is released. Linux files and Turso databases are unaffected.
  - A provisioning retry mints a new token for the same database, whose URL does not change, and the cache keeps a client opened with the earlier token. Melos mints tokens with `expiration=never` and never invalidates them, so that token keeps working. Invalidating a database's tokens with `auth/rotate` (ADR-031) would leave such clients failing until their instance recycles, so a rotation must first evict them in every instance.
  - The cache is per server instance: on Vercel each function instance opens a workspace's client on its first request for that workspace, and no instance invalidates another's.
- `MigrationRunner` (`src/server/db/migration-runner.ts`) applies a batch across every `active` workspace, one workspace at a time. A batch has a ULID `batch_id` and a target version, the highest embedded workspace migration (step 3 of provisioning). Each run of the batch appends `migration.batch_started` with `target_type` `migration_batch`, `target_id` the batch id and `after_json` `{"to_version": <target>}`. While the workspace host is `unconfigured` (ADR-031), a batch throws `WorkspaceHostConfigError`, naming the missing variables, before it appends that row or claims a workspace, so a missing host never marks a workspace `failed`. Per workspace:
  1. At the target version: insert a `skipped` `migration_runs` row. The database is not opened.
  2. Otherwise claim the row (ADR-033): in one `melos-control` transaction set `status = 'migrating'` and insert a `running` `migration_runs` row (`mig_<ulid>`, `from_version`, `to_version`) through IntegrityGuard. A run's `from_version` is the registry's `schema_version` when the run claimed or skipped the workspace.
  3. Open the database with the workspace host setting and token decryption that provisioning uses, not the `TenantContextResolver` cache. Read the database's version and, when the registry differs, set `schema_version` to it. Apply the pending versions in one transaction per version and set `schema_version` after each.
  4. In one transaction, return the row to `active` with a `succeeded` run, or set `failed` with the last version the database committed as `schema_version`, with `status_detail` `batch <batchId> failed: <error>` and a `failed` run whose `error` holds the same error name and code. Stored and reported errors never hold a message, which may contain a token or database URL.
- A rerun of the batch skips workspaces already at the target version. It also retries each workspace the batch left `failed`, which is no longer `active`: a `failed` row whose `attempt_id` names a `failed` run of the batch. It takes over a `migrating` row whose `attempt_id` names a `running` run of the batch once the row has been silent for `STALE_CLAIM_MS` (TEN-005, ADR-033). A workspace that failed provisioning (P-23), or that a provisioning retry claimed after the batch failed it, is retried with `npm run workspace:provision`.
- Operators run a batch with `npm run db:migrate-workspaces` and rerun one with `npm run db:migrate-workspaces -- <batchId>`, against one environment's control database; deploys never run it. `scripts/migrate-workspaces.ts` runs under `tsx` through `scripts/operator.ts`, which checks the arguments before any app module loads and prints only error names and codes, never a message or stack. It prints `batch <batchId>`, then `<workspaceId> <from_version> <to_version> <status> <error>` for each workspace, where `<error>` is an error name and code or `-`. It exits 0 only when every workspace it takes ends `succeeded` or `skipped`, and so at the target version; 1 when one is `unclaimed` or `failed`, which can leave it `active` below the target, or when the batch stops; and 2 for a usage or configuration error, a batch id that is not a ULID, a remote control database while the workspace host is `local`, or an `unconfigured` workspace host, for which it prints only the names of the missing variables.

### 7.3 Agent memory scoping

`melos-agent-runtime` is shared by all workspaces (BP §4.1, TEN-006), so isolation comes from resource scoping and thread ownership, not from separate databases. Mastra storage is configured with the agent database only, and `parseServerEnv` refuses a `MELOS_AGENT_DATABASE_URL` that opens the control database, comparing where `@libsql/client` sends each one's queries: a file URL's resolved path, or, for a remote URL expanded and encoded by `@libsql/core`, the directory HTTP resolves `v2/pipeline` against or the URL a WebSocket opens, both on the HTTP scheme, so percent-encoding, `libsql:` and default ports change nothing; an in-memory URL never matches; workspace URLs are generated per workspace (§7.2), so neither can name one.

- The memory resource ID is `<workspaceId>:<userId>`, passed as `resourceId` to `getLocalAgents` (§7.1). `@ag-ui/mastra` sends `memory: { thread: threadId, resource: resourceId }` on each run and falls back to `resource: threadId` when no resource ID is configured ([SRC-064](https://www.npmjs.com/package/@ag-ui/mastra), `dist`), so the route always sets it (TEN-007).
- Thread IDs come from the CopilotKit client. `MelosAgentRunner` enforces thread ownership on run, connect and stop before any Mastra call (§7.9, TEN-009). Whether Mastra memory itself rejects a thread owned by another resource on the embedded path is U-22. The Mastra server's thread-ownership checks ([SRC-036](https://mastra.ai/docs/server/middleware)) apply only to Mastra server routes, which this topology does not expose.
- Working memory uses resource scope, which is the default and persists across threads for the same resource ([SRC-039](https://mastra.ai/docs/memory/working-memory)). Its schema holds preferences only: tone, signature, preferred report preset. Agent instructions forbid storing catalog, rights or contact facts in memory; those always come from tools (TS §23).
- Semantic recall stays disabled, which is the default ([SRC-040](https://mastra.ai/docs/memory/semantic-recall)) (P-12). If enabled later, it uses `scope: 'resource'`.
- No Mastra server routes and no Studio are reachable in production; Studio runs only in local development (AUTH-009). Traces and logs in the runtime database contain tool output from all workspaces and are operator-only.
- Deleting a workspace deletes Mastra threads and `agent_threads` rows whose resource ID starts with `<workspaceId>:`.

### 7.4 Approval flow

1. A tool that needs approval (§3.2, §6.3) validates the input and loads the current state without writing. It computes:
   - `inputHash`: SHA-256 of the tool name and the canonical JSON input;
   - `beforeHash`: SHA-256 of the canonical JSON of every row the write would change (the full current share set for share tools; the message row, its recipients and status for `sendMessage`);
   - `contentHash` (`sendMessage` only): SHA-256 of subject, body text, body HTML and the recipients sorted by type and address.
2. It writes `approval.requested` to `audit_log` and suspends with the `ApprovalRequest`: `return await context.agent.suspend(request)`. Mastra exposes `suspend` and `resumeData` on `context.agent` and requires returning right after `suspend` ([SRC-042](https://mastra.ai/docs/agents/human-in-the-loop)). `suspendSchema` is `ApprovalRequest` and `resumeSchema` is `ApprovalDecision` ([SRC-038](https://mastra.ai/reference/tools/create-tool)).
3. `@ag-ui/mastra` surfaces the suspension as an AG-UI interrupt: a structured `RunFinishedEvent.outcome` of type `interrupt` plus the legacy `on_interrupt` custom event. It resumes from `RunAgentInput.resume` or `forwardedProps.command.resume`. The structured path needs a CopilotKit client of at least 1.61.2; the pinned 1.71.1 satisfies it ([SRC-064](https://www.npmjs.com/package/@ag-ui/mastra) README).
4. The frontend renders `ConfirmationCard` with `useInterrupt` from `@copilotkit/react-core/v2`. The render function receives `{ event, resolve }`; for Mastra the payload is `event.value.suspendPayload` on the legacy shape or the interrupt object on the standard shape, and `resolve(payload, interruptId)` returns the payload to the suspended tool ([SRC-057](https://docs.copilotkit.ai/mastra/human-in-the-loop/useInterrupt)).
5. Approve and Decline both call `resolve` with an `ApprovalDecision` (`approved`, `inputHash`). Closing the card resolves with `approved: false`. A decline therefore always resumes the tool.
6. On resume the tool reads `context.agent.resumeData` ([SRC-042](https://mastra.ai/docs/agents/human-in-the-loop)):
   - `inputHash` differs from the request: nothing is written; `approval.declined` is audited with reason `input_mismatch`.
   - `approved: false`: nothing is written; `approval.declined` is audited; the tool returns a declined result.
   - `approved: true`: in one transaction the service re-reads the rows and recomputes `beforeHash` (and `contentHash`). A mismatch writes nothing to the domain tables, audits `approval.stale` and returns `STATE_CHANGED`, so the agent re-reads and proposes again (AUD-003). A match performs the mutation and writes `approval.granted` plus the mutation's audit rows in the same transaction.
7. An interrupt nobody resolves leaves only `approval.requested`. The resume may arrive on a different instance (TEN-011, §7.9).
8. Tool results render through `useRenderTool` from `@copilotkit/react-core/v2`, keyed by tool name, receiving `status` and `args` ([SRC-062](https://docs.copilotkit.ai/mastra/generative-ui/backend-tools)). How the render callback receives the tool result is U-03.

### 7.5 Email and asset adapters

Owner decision 2026-09-12: Resend and Cloudflare R2 are the first production adapters (ADR-011, ADR-012).

```ts
interface EmailTransport {
  readonly provider: "sandbox" | "resend";
  send(input: {
    messageId: string;          // idempotency key
    from: string;
    to: string[]; cc: string[]; bcc: string[];
    subject: string;
    bodyText: string;
    bodyHtml?: string;
  }): Promise<{ providerMessageId: string; providerThreadId?: string; acceptedAt: string }>;
}

interface AssetStorage {
  readonly provider: "local" | "r2";
  createUploadUrl(input: { workspaceId: string; storageKey: string; contentType: string; expiresInSeconds: number }): Promise<{ url: string }>;
  createDownloadUrl(input: { workspaceId: string; storageKey: string; expiresInSeconds: number }): Promise<{ url: string }>;
  put(input: { workspaceId: string; storageKey: string; contentType: string; body: Uint8Array }): Promise<void>;
  delete(input: { workspaceId: string; storageKey: string }): Promise<void>;
}
```

- **Sending.** The approval transaction moves the message from `draft` to `queued`; the transport call then moves it through `sending` to `sent` or `failed`. `updateMessageDraft` only edits `draft` messages. `ResendEmailTransport` passes `messageId` as the Resend idempotency key. Resend accepts keys up to 256 characters, keeps them for 24 hours, returns the original email id for a repeated key with the same payload, and answers 409 `invalid_idempotent_request` when the payload differs ([SRC-098](https://resend.com/docs/dashboard/emails/idempotency-keys)). A 409 marks the message `failed` with `IDEMPOTENCY_CONFLICT`. Only a `queued` message is sent, so a retry after 24 hours cannot send twice. Production sending-domain verification is U-28.
- **Sandbox.** `SandboxEmailTransport` makes no network calls. It returns `providerMessageId = sandbox_<messageId>` and `providerThreadId = sandbox_thread_<pitchId>`, stores the payload under `.data/sandbox-outbox/<workspaceId>/<messageId>.json` in development and in memory in tests, and returns the stored result for a repeated `messageId`. `OutreachService.simulateInboundReply(messageId, bodyText)` exists only when the sandbox transport is active; it creates an inbound message and a `reply_received` pitch event (OUT-003). Production reply ingestion is U-29.
- **Asset keys (AST-001).** `AssetService` generates every key as `<workspaceId>/<assetId>/<sanitized file name>` from the workspace resolved for the request; clients never supply keys. Every `AssetStorage` method refuses a key that does not start with `<workspaceId>/` for that workspace. A presigned URL is bound to its object key, so a signed PUT cannot write elsewhere ([SRC-099](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)).
- **R2 (AST-002).** `R2AssetStorage` generates presigned GET and PUT URLs on the server with R2 API credentials and AWS Signature Version 4; R2 accepts expiries from 1 second to 7 days ([SRC-099](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)). Melos signs audio downloads for 3600 seconds, other downloads for 300 seconds and uploads for 900 seconds, with one private bucket per environment (P-35). When a media request fails to load (an expired URL answers 403), `AudioPlayer` requests a fresh URL and retries once. S3 client and endpoint configuration is U-27. `LocalAssetStorage` serves files from `.data/assets/` through an authenticated route in development and tests.
- **Selection.**

| Environment | `MELOS_EMAIL_TRANSPORT` | `MELOS_ASSET_STORAGE` |
|---|---|---|
| Development, tests | `sandbox` | `local` |
| Vercel preview | `sandbox` (P-34) | `r2`, preview bucket (P-34) |
| Vercel production | `resend` | `r2`, production bucket |

Production startup fails when either variable selects `sandbox` or `local` (owner decision 2026-09-12).

**Auth email and sign-up.** Better Auth's verification and invitation emails go through `sendAuthEmail` (`src/server/auth/mailer.ts`), selected by `MELOS_AUTH_MAILER`: `outbox` (development default, `.data/auth-outbox/`), `memory` (tests) or `disabled`, which sends and writes nothing. Until phase 8 wires Resend, production startup accepts only `disabled` (owner decision 2026-09-12): sign-up sends no verification email, and a `hooks.before` handler refuses `/organization/invite-member` with 403 `INVITATIONS_UNAVAILABLE` before Better Auth writes or extends an invitation. `MELOS_SIGNUP_ALLOWED_EMAILS` lists the addresses that may sign up, comma-separated and compared case-insensitively; `databaseHooks.user.create.before`, which every Better Auth user-creation path runs, refuses any other address with 422 `SIGN_UP_NOT_ALLOWED`. Unset, anyone may sign up outside production and nobody may in production. Signing in never consults the list.

### 7.6 Import pipeline (Airtable and CSV)

Owner decisions 2026-09-12. One pipeline, two readers.

**Stages.**

1. **Read.** The Airtable reader loads all eight legacy tables from the base with a personal access token supplied for this run and not persisted (P-16). Airtable Web API endpoints, pagination and rate limits are U-10. The CSV reader loads an uploaded file stored as an `assets` row (`asset_type = 'import_source'`).
2. **Snapshot.** Records normalize into one snapshot; `source_snapshot_sha256` identifies it.
3. **Map.** Rows map to canonical entities by §4.5 (Airtable) or the CSV template below. Each target gets a `target_role`, a `target_key` and a payload hash:
   - several targets of one role from one source row use `target_key` = the normalized party name from that row (writers, publishers, master owners, artists) or `<role>:<normalized name>` (recording credits);
   - all other targets use `''`;
   - share targets store their natural key in `entity_id` (§4.4).
4. **Plan.** Each mapped target is compared with `external_references` (P-19). The *current hash* is SHA-256 of the canonical JSON (sorted keys) of the target's mapped fields as read from Melos now, by the same reader that sets `applied_row_sha256`:
   - `create`: no reference;
   - `unchanged`: `source_payload_sha256` equals the stored value; nothing is written;
   - `update`: the payload hash differs and the current hash equals `applied_row_sha256`;
   - `conflict`: the payload hash differs and the current hash differs from `applied_row_sha256`, meaning the row was edited in Melos. A referenced target that was hard-deleted or soft-deleted in Melos counts as edited (`MELOS_TARGET_DELETED`, `MELOS_TARGET_SOFT_DELETED`) and is never recreated or restored;
   - `orphaned` (P-40): a reference for this `source_system` and `source_container` whose (`source_table`, `source_record_id`, `target_role`, `target_key`) the current snapshot no longer produces, such as a writer removed at the source. A rename is one `orphaned` target plus one `create`. When the current hash equals `applied_row_sha256`, apply removes the target and its reference: relationship targets (shares, contributor roles, credits, artists, links, terms, licensing contacts) are deleted through `IntegrityGuard`; entity targets (parties, compositions, recordings, releases, contacts) are soft-deleted when the guard allows it and otherwise reported; pitch cells and pitch events are never removed and are reported as `SOURCE_TARGET_REMOVED`. When the hashes differ, the target is a `conflict`. An Airtable snapshot always holds every table. A CSV upload produces `orphaned` targets for missing rows only when the user marks it as the full catalog for its source key (`import_runs.full_snapshot = 1`). For missing rows and for rows that are present alike, a target kind can become `orphaned` only when the column that produces it is present and mapped in that file's header: a writer dropped from a mapped `writers` column is `orphaned`, while a file without a `writers` column changes no writer targets. An absent or unmapped column means no change to that kind.
5. **Validate.** Issues by severity. Error codes block apply: `UNKNOWN_PITCH_STATUS`, `DUPLICATE_ISRC`, `DUPLICATE_ISWC`, `INVALID_ISRC`, `INVALID_ISWC`, `SHARE_OUT_OF_RANGE`, `SHARE_SCALE_AMBIGUOUS` (U-17), `CSV_ROW_WITHOUT_IDENTITY`, `CSV_UNMAPPED_REQUIRED_COLUMN`. Warnings: `SHARE_TOTAL_INCOMPLETE`, `SHARE_TOTAL_OVER`, `UPC_LEADING_ZERO_RISK`, `PARTY_KIND_UNCERTAIN`, `PARTY_MATCH_UNCERTAIN`, `POSSIBLE_DUPLICATE_COMPOSITION`, `BLANK_PITCH_STATUS`, `UNPARSEABLE_DURATION`, `MELOS_EDIT_CONFLICT`, `MELOS_TARGET_DELETED`, `MELOS_TARGET_SOFT_DELETED`, `SOURCE_TARGET_REMOVED`, `ARTWORK_WITHOUT_RELEASE`. Info: `FORMULA_VALUE_NOT_IMPORTED`, `LEGACY_ONE_STOP_MISMATCH`, `WEBSITE_TYPED_AS_EMAIL`.
6. **Dry-run result.** `import_runs` (`mode = 'dry_run'`) with `planned_json`, plus `import_issues`. Nothing else is written (IMP-002). `ImportReport` shows create, update, unchanged, orphaned and conflict counts per target table, and the issues.
7. **Apply.** Requires `import:run`, a dry-run with zero errors for the same source hash (a changed source returns `blocked`), and a `ConfirmationCard` confirmation (IMP-003). Writes run through the same services as manual edits, so `IntegrityGuard`, validation and `audit_log` apply (`import.apply` plus per-entity actions with `actor_type = 'import'`). After each write, in the same transaction, the importer re-reads the target and stores its hash as `applied_row_sha256`, so the hash covers values after normalization (an uppercased ISRC, a percent converted to basis points). Imported pitch statuses write `pitch_events` with `event_type = 'imported'`. Attachments copy to `AssetStorage` during apply; Airtable attachment URL lifetime is U-16. CSV apply commits at most 500 rows per transaction and records `resume_cursor` (IMP-013).
8. **Re-import.** Same stages. `external_references` makes it idempotent: `unchanged` targets are skipped, unedited `orphaned` targets are removed as in stage 4, and `conflict` targets are left untouched and reported (IMP-004).

**Airtable specifics.** SONGS split rules, Creatives classification and report checkboxes follow §4.5 and IMP-006 to IMP-010. Party classification (P-22): a Creatives row becomes an organization when it is referenced only through Publishing or MasterOwner junctions and has no Songwriter Name; a row with a Songwriter Name, or referenced through Songwriting, becomes a person; any other row becomes a person and raises `PARTY_KIND_UNCERTAIN`. A non-empty Publisher Name creates a separate organization party, matched by normalized name plus publisher IPI. Report checkboxes: each distinct combination of the eight section checkboxes maps to the `full`, `sans_lyrics` or `just_lyrics` preset when it matches, otherwise to one imported template named "Imported: <enabled sections>"; the song keeps a link to it in `external_references.metadata_json.reportTemplateId` (P-17).

**CSV template (P-26).** One row per recording. Headers not in this list go through a column-mapping step during the dry-run; unmapped required columns are errors.

### 7.9 CopilotKit agent runner on Vercel

**Problem.**

- `InMemoryAgentRunner`, the default, keeps every thread in one process-global store (`ɵGLOBAL_STORE`) keyed by thread id alone. `connect` replays that store and `stop` aborts by thread id ([SRC-092]: `v2/runtime/runner/in-memory.mjs`; `handlers/sse/connect.mjs` calls `runner.connect({ threadId, agentId, headers })`). CopilotKit documents that its history is not shared across instances ([SRC-096](https://docs.copilotkit.ai/backend/agent-runner)).
- With that runner, the runtime also serves `/threads`, `/threads/:id/messages`, `/threads/:id/events`, `/threads/:id/state` and `/threads/clear` from the same store for every caller ([SRC-092]: `handlers/intelligence/threads.mjs`), so any signed-in user could list or clear other workspaces' threads.
- On Vercel, several invocations can share one instance and traffic scales across instances ([SRC-097](https://vercel.com/docs/fluid-compute)), so a reconnect or a stop can reach an instance that never saw the run.
- `SqliteAgentRunner` persists runs to a local SQLite file through `better-sqlite3` so history survives restarts "on a single instance" ([SRC-096](https://docs.copilotkit.ai/backend/agent-runner), [SRC-101]). `IntelligenceAgentRunner` requires CopilotKit Intelligence, which is not part of the stack.

**Decision (ADR-023).** `MelosAgentRunner` extends `AgentRunner` from `@copilotkit/runtime/v2`, whose abstract methods are `run`, `connect`, `isRunning` and `stop` ([SRC-096](https://docs.copilotkit.ai/backend/agent-runner)). The route constructs it per request with the resolved tenant and passes it as `runner` in the `CopilotRuntime` options ([SRC-092]: `runner?: AgentRunner` in `core/runtime.d.mts`).

- **Ownership (TEN-009).**
  - `run`: in one `melos-agent-runtime` transaction, insert the `agent_threads` row (`thread_id`, `resource_id`, `workspace_id`, `agent_id`) if absent. If the row exists with a different `resource_id`, throw before the agent starts. If `active_run_id` is set and the heartbeat is fresh, throw `Thread already running`, which matches the in-memory runner's default ([SRC-096](https://docs.copilotkit.ai/backend/agent-runner)). Otherwise take the thread with a compare-and-set: `UPDATE agent_threads SET active_run_id = :runId, run_instance_id = :instance, run_heartbeat_at = :now, stop_requested_at = NULL WHERE thread_id = :threadId AND resource_id = :resourceId AND (active_run_id IS NULL OR run_heartbeat_at < :staleBefore)`. Zero affected rows means another request took the thread first, and `run` throws `Thread already running` (P-32).
  - `connect`, `isRunning`, `stop`: read with `WHERE thread_id = ? AND resource_id = ?`. With no row, `connect` returns an empty completed stream and `isRunning` and `stop` return false, so nothing reveals whether another workspace uses the thread id.
- **Route guard.** `createCopilotRuntimeHandler` accepts `hooks.onBeforeHandler`, which runs after routing with the route info and short-circuits when it throws a `Response` ([SRC-092]: `core/hooks.d.mts`). It returns 404 for every route except `info`, `agent/run`, `agent/connect` and `agent/stop` (TEN-012, ADR-027). The allowlist matters most for `agent/suggest`: that handler clones the agent and calls `runAgent` directly with the client's `threadId`, bypassing `runtime.runner` ([SRC-092]: `handlers/handle-suggest.mjs`, `core/fetch-handler.mjs`), so `MelosAgentRunner` could not check ownership and `MastraAgent` would read and write memory for that thread. The CopilotKit client generates suggestions only for a registered dynamic suggestions config, one with `instructions` ([SRC-107]); Melos registers none. The same allowlist covers `threads/*` and `memories/*`. `MelosAgentRunner` does not set `ɵsupportsLocalThreadEndpoints`, so the runtime has no local thread backend either ([SRC-092]: `runner/agent-runner.mjs`, `handlers/intelligence/threads.mjs`).
- **History (TEN-010).** When a run finishes, is interrupted, errors or stops, the runner compacts its events with `compactEvents` from `@ag-ui/client`, the helper the in-memory runner uses ([SRC-092]). It inserts one `agent_thread_runs` row with the next `seq` and clears `active_run_id` in the same transaction, conditioned on `active_run_id = :runId`. The agent run is not tied to the HTTP response: on a client disconnect `createSseEventResponse` only unsubscribes from the runner's observable ([SRC-092]: `handlers/shared/sse-response.mjs`), and the runner keeps the agent running. `run` registers the run's completion promise, finalization included, with `after()` from `next/server`, which on Vercel keeps the invocation alive through `waitUntil` for up to the route's `maxDuration` ([SRC-105](https://nextjs.org/docs/app/api-reference/functions/after), [SRC-106](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package)). Whether that holds after a client disconnect on a streaming route is U-30. `connect` replays every run of the thread in `seq` order.
- **Live tail.** A module-level map keyed by `resourceId|threadId` holds the event subject of each run active on this instance. `connect` on that instance replays history, then tails the live run. `connect` on another instance while the run is active replays finished runs, then polls `agent_thread_runs` once per second until the active run's row appears (it emits that run's events and completes) or the run's heartbeat goes stale (it completes). If the request would reach `maxDuration` first, it emits the custom AG-UI event `melos.run_pending` (`threadId`, `runId`) and completes; the chat shell handles that event by calling connect again after 2 seconds, at most 5 times (P-41). Whether the CopilotKit client exposes that custom event to the app is U-23.
- **Stop.** On the owning instance `stop` aborts the agent. On another instance it sets `stop_requested_at`; the running instance checks its row at least once per second and aborts (P-32, U-24).
- **Liveness.** The running instance refreshes the heartbeat every 10 seconds with `UPDATE agent_threads SET run_heartbeat_at = :now WHERE thread_id = :threadId AND active_run_id = :runId`. A heartbeat older than 30 seconds marks the run dead, so another request may take the thread through the compare-and-set above. When a heartbeat or finalization update affects zero rows, the run has lost the thread: it aborts the agent and writes nothing further (P-32).

**Approvals across instances (TEN-011).** A suspended tool ends the SSE run with an interrupt outcome. The resume arrives later as a new run request that may land on another instance, and `@ag-ui/mastra` then calls `agent.resumeStream(resume, ...)` ([SRC-064](https://www.npmjs.com/package/@ag-ui/mastra), `dist`). Mastra documents that suspended runs survive restarts only with a persistent storage provider ([SRC-042](https://mastra.ai/docs/agents/human-in-the-loop)), so `melos-agent-runtime` is a Turso Cloud database in every deployed environment (P-33). U-25 proves resume on a different instance.

**Duration.** The route sets `maxDuration` to 300 seconds, the Fluid compute default on every plan ([SRC-097](https://vercel.com/docs/fluid-compute)). A run still going at that point is cut and recorded with status `error` (P-32).
